# Security and safety of this tool

Implemented extension repository-v2 (D-25): literal defaults, a literal cast only to existing supported built-in types, exact zero-argument gen_random_uuid/pg_catalog.gen_random_uuid and now/pg_catalog.now, unmodified CURRENT_TIMESTAMP, ordinary btree column indexes, ADD COLUMN with existing types/constraints, and DROP POLICY RESTRICT followed by ordered recreation. Expression/partial/concurrent/opclass/collation indexes and arbitrary default functions remain rejected. Storage schemas/policies, custom functions/triggers/extensions/DO and any unsupported statement reject the complete chain; no safe prefix is replayed. This finite subset defines implemented admission coverage.

Literal defaults also undergo credential checks with their AST column-name context, including casts, before replay. Static SQL-default detection preserves credential results independently of admission and consumes SQL doubled quotes as one literal. Secret-bearing executable defaults are rejected, never masked and executed. Import metadata gets its final redaction projection before persistence; the existing sink guard remains mandatory.

Repository discovery has separate bounds: 500 eligible files, 10 MiB combined, 2 MiB/file; 20,000 tree entries and 8 MiB metadata responses; 15-second per-request/subprocess timeout and 120-second import deadline. Source/config and SQL get credential analysis in batches of at most 200. The existing **2 MiB combined executable SQL/parser limit remains unchanged** and is a visible RLS coverage limitation, even if a larger repository fits the source import budget. Oversized/excluded migration files make their chain incomplete. Symlinks/submodules are excluded; local reads check ancestors, real paths, file handles and byte sizes. Concurrent filesystem mutation aborts a fresh run; this is saved-file discovery, not an atomic OS filesystem snapshot. Unknown GitHub tree keys/duplicate JSON keys, invalid URL/ref/path, redirects and hash/size mismatches fail closed. Repository code, hooks, dependencies, archives and discovered credentials are never executed or used.

Requirements: FR-1, FR-3, FR-11, FR-15, FR-19, FR-22; NFR-1–NFR-3/NFR-8/NFR-9. This is a design threat model, not a completed audit or security certification.

## Assets, adversaries and boundaries

Assets: submitted source secrets, developer intent, integrity of evidence/approvals, operator host, container control, synthetic experiment reproducibility and local reports. Adversaries may control uploaded schema, policy names/comments, source files, filenames, manifest contents or text reaching Gemma. A malicious web page can try to reach the localhost API. Model output is untrusted regardless of source. The local operator controls approvals; that does not make uploaded SQL trustworthy.

Boundaries: browser → local API; transient raw intake → redacted persistence/model; SQL AST → restricted loader; worker → isolated replica; model → strict JSON/reference validation; human review → digest-bound patch action. Docker/container isolation is a defense layer, not a claim that arbitrary untrusted SQL is safe to execute on a laptop.

## SQL admission profile

Accept only schema-only UTF-8 SQL with an explicit ordered file manifest. Parse with a PostgreSQL AST parser backed by libpg_query (`pgsql-parser`, pinned to a PostgreSQL-17-compatible grammar). If that compatibility check fails, block intake until a supported binding/version is selected; do not fall back to regex validation. This parser family uses the actual PostgreSQL parser, but parsing alone is not authorization. [libpg_query project](https://github.com/pganalyze/libpg_query).

The implemented allowlist admits application schemas, supported primitive base tables/constraints, RLS flags, supported policies, limited table/schema grants, and the finite repository-v2 forms above. Enum/identity/sequence admission and general column/sequence privilege coverage remain broader design targets. Unsupported AST nodes fail closed; parsing alone never authorizes execution.

Comments are inert and removed from executable AST rendering. SQL comments may be sampled after redaction for adversarial tests but never become manifest declarations. Incoming COMMENT statements are rejected in the default executable profile; callers may remove them before upload. Input transaction wrappers and SQL `SET` statements are rejected with a location and reason; the loader owns transactions/settings. This accepts supported schema dumps, not every output of every `pg_dump` version. psql meta-commands, ownership headers, data sections and unsupported dump statements must be removed by the user or a future reviewed normalizer; never silently delete semantically relevant statements.

The current expression AST allowlist accepts constants, single-column references, boolean AND/OR/NOT, NULL checks, built-in comparisons/BETWEEN/finite IN, trusted `auth.uid()`, `auth.role()`, `auth.jwt()` and `length`/`pg_catalog.length`, plus bounded one-target scalar SELECT wrappers without FROM. Executable defaults use the separate literal/exact UUID/time allowlist above. Unknown nodes/operators/functions fail closed; the finite implementation is in [admit.ts](../packages/core/src/intake/admit.ts).

Broader design targets include general supported casts, bounded scalar/EXISTS subqueries over admitted base tables, approved JSON field extraction and validated owned-sequence defaults. They do not describe achieved admission coverage. Recursive CTEs, custom operators/types, arbitrary functions, system-catalogue access from user expressions and external access remain rejected.

Reject CREATE FUNCTION/PROCEDURE, DO, trigger/rule creation, SECURITY DEFINER code, extensions, COPY (including PROGRAM), large-object/file APIs, FDWs/dblink, subscriptions, event triggers, role/user/database operations, ALTER SYSTEM, LOAD, custom language, arbitrary DML, data COPY, shell/meta commands and settings/search_path changes. This is a compatibility limitation visible to the user, not evidence that their project is vulnerable. Do not execute a “safe prefix” of a rejected file. Apply admitted schema in one managed transaction with schema-loader privileges; fail atomically. Admission runs with memory/depth/statement limits before any container execution; raw parser errors are converted into fixed messages.

## RLS detection

Implemented scope: loader-owned admitted base tables, columns/constraints/policies and effective table/schema grants, including PUBLIC. The broader role/helper/column-grant/sequence inventory and RLS-005/007 heuristics below are design targets outside achieved coverage . A suspicious fact is not a confirmed vulnerability; current valid expected-deny/observed-allow evidence is required.

Requirements: FR-4–FR-7, FR-13. Catalogue analysis identifies potentially over-broad behavior, not a vulnerability. The engine tests every supported established expectation even when no static rule fired; a mismatch can create a finding with `RLS-009`.

### Catalogue snapshot

Run after all admitted migrations commit and before seeding, using a trusted catalogue connection. Query only schemas selected from the admitted manifest; parameters hold schema arrays, never interpolated SQL. Preserve schema-qualified names, OIDs within this snapshot, and exact deparsed conditions. Redact any sensitive literal before storing or model delivery. OIDs are not stable across replicas; normalized names define snapshot digests.

Also inventory `pg_trigger` (exclude system FK triggers), views, partition inheritance, domains (`pg_type.typbasetype`, constraints), and referenced functions (`pg_proc` identity, language, `prosecdef`, owner, configuration) to enforce the compatibility boundary. Effective per-column SELECT/UPDATE/INSERT privileges come from `has_column_privilege`; inspect sequence USAGE/SELECT for defaults using `has_sequence_privilege`. A table-grant result alone must not misclassify column-only access or an inaccessible identity sequence. `information_schema.role_table_grants` alone is insufficient for inherited/PUBLIC access.

[PostgreSQL pg_policies](https://www.postgresql.org/docs/17/view-pg-policies.html) defines the catalogue fields. [Row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) documents default denial and owner/BYPASSRLS behavior. Do not change grants or enable FORCE RLS merely to make a probe produce the expected result.

### Effective policy reasoning

For each table/actor/command, expand `ALL`, resolve direct/PUBLIC/inherited role applicability, and preserve permissive/restrictive grouping. Effective eligibility requires ordinary privileges plus at least one applicable permissive policy; applicable permissive policies combine with OR and restrictive policies with AND. RLS enabled with no applicable policy is default deny. RLS disabled means policy expressions do not filter access. Table owners normally bypass RLS unless forced; superuser/BYPASSRLS bypass is never a valid test identity.

SELECT/DELETE use `USING`; INSERT validates new rows with `WITH CHECK`; UPDATE evaluates old-row eligibility and new-row checks and can also depend on SELECT visibility. An omitted WITH CHECK on UPDATE/ALL inherits USING; its absence is not by itself a bypass. Preserve this effective condition in the snapshot. [CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html), [Supabase RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security).

Recognize simple constants/boolean structure through a PostgreSQL AST, including redundant parentheses and casts. Do not use substring searches for `true` or `auth.uid` as a correctness proof. Policy text containing `auth.uid()` may still be permissive through an OR branch. Arbitrary expression equivalence, function behavior and business intent are not statically decidable here. Unsupported expressions yield a visible uncertainty and a compatibility check before execution.

### Severity, confidence and limits

Default confirmed private cross-user read/write/delete: high; anonymous access to declared-private rows: high; critical only when a human-declared sensitivity/impact statement justifies it, never from a table name or AI alone. Intentionally-public matching facts are info/suppressed. Inferred intent keeps the severity conditional and confidence at most medium even if observation confidence is high. Declared intent + exact target/control evidence supports high confidence. Unknown intent stays low confidence. `severity_basis` records static/observed/developer-declared basis; AI severity stays advisory in `ai_analysis`.

Snapshot hash includes canonical policy/grant/type/constraint/function identities, excludes transient OIDs and timestamps, and uses sorted UTF-8 JSON with stable keys. Actual schema hash is recorded separately from uploaded bytes so loader/environment differences are visible.

Limitations: synthetic rows do not cover all predicate branches; real data and custom claims differ; local auth helpers do not reproduce auth hooks; unsupported extensions/functions/views/partitions are not silently approximated; storage and edge functions are outside v1. Direct table access does not prove the application's deployed API exposes the same operation. Record these limitations on every run, including successful ones.

## Credential detection and redaction

Requirements: FR-2, FR-3, FR-23; no replica or network credential probes. The finding is about submitted artifact exposure, never validity of a key or compromise of an account.

### Detection and contextual classification

Bounded UTF-8 text scan, using token/literal extraction for supported JavaScript/TypeScript/JSON/env/YAML/TOML and line scanning for other admitted text. Recognize multiline PEM material before line-level scanning. Do not execute a parser hook or import the user's project. A parse error falls back to bounded text scanning and records reduced context confidence.

| Rule    | Candidate family and detector                                                                                                                 | Context that determines result                                                                                                                                            |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SEC-001 | Provider-prefixed API token shapes from a versioned grammar catalogue; generic assigned secret literals of ≥20 characters with entropy signal | Provider, variable name, client/server location, initializer/header use; entropy alone cannot confirm.                                                                    |
| SEC-002 | Database connection URI with nonempty password, or password assignment associated with a DB host/user                                         | Redact the entire URI/token; distinguish runtime environment lookup from committed literal.                                                                               |
| SEC-003 | Three-part JWT-like token, JWT signing-secret assignment, authorization bearer literal                                                        | Decode header/payload in memory within bounds; role claim is unverified metadata; public anon/publishable tokens are not privileged secrets merely because they are JWTs. |
| SEC-004 | PEM private-key delimiters and content, including escaped newline form                                                                        | Public-key/certificate blocks are not private keys; parse shape, never perform signing or print material.                                                                 |
| SEC-005 | OAuth client secret / cloud credential assignments and recognized paired cloud ID+secret context                                              | Client ID alone is public; an ID paired with a secret raises confidence; account privilege remains apparent.                                                              |
| SEC-006 | Privileged backend credential in a client-exposed location (e.g. service-role context or a recognized secret-key family)                      | Require literal or resolvable bundled value plus privilege/context signals; `NEXT_PUBLIC_` name alone with no value is a configuration warning, not a found secret.       |
| SEC-007 | Generic sensitive assignment with insufficient family certainty                                                                               | `unknown_secret`, suspected and low confidence; do not label as a valid API key.                                                                                          |

Maintain pattern metadata (`rule_version`, `family`, `prefix`, `length_bounds`, `alphabet`, `public_counterexamples`) in the detector registry. Before adding or changing provider-specific claims, verify official provider documentation and add negative public-token cases. No live endpoint validation is permitted. The initial provider-specific distinction is Supabase secret/service-role versus publishable/anon; other families use the bounded contextual rules below, not invented assertions about a vendor's exact key grammar. Supabase documents publishable/anon keys for public clients and secret/service-role keys for privileged server use. Browser rejection of a secret key does not make publishing it appropriate; this tool does not test that key. [Supabase API keys](https://supabase.com/docs/guides/api/api-keys).

#### Initial deterministic candidate rules

These are bounded candidate heuristics, not provider validity checks (D-18). Normalize identifiers by splitting camel case and `_`/`-`, then lowercase; retain the original variable name only after redaction. Literal extraction is bounded to 64 KiB/value. Exact placeholder/public classification runs after candidate collection so candidate recall and exposure classification can be measured separately.

| Family                      | Initial matching rule                                                                                                                                                                                                                                                                                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| API/generic assigned secret | Name contains the token sequence `api key`, `access token`, `auth token`, `secret`, or `password`; literal length 20–4096 and Shannon entropy ≥3.5 bits/character is a strong candidate. A sensitive name plus a literal of ≥8 characters is a weaker SEC-007 candidate even below that entropy.                                                                   |
| Supabase key context        | Literal starts `sb_secret_` or `sb_publishable_` with a nonempty suffix of at most 4,096 characters: classify family from prefix, never authenticate. A literal bound to normalized `service role key`/`supabase service role key` is privileged-context evidence, not proof of validity. Public prefixes/legacy anon roles are negative exposure counterexamples. |
| DB credentials              | URI scheme `postgres`, `postgresql`, `mysql` or `mongodb` with password-bearing userinfo; or literal assignment to `database password`, `db password` or `pgpassword`. Classify only credential exposure; no database engine coverage is implied. Redact the entire URI.                                                                                           |
| JWT-like material           | Three nonempty base64url-like segments separated by two dots, total ≤16 KiB; bounded decode of header/payload may establish unverified claim context. A signing-secret candidate uses the variable token sequences `jwt secret` or `jwt signing key`. Neither decoding nor a role claim validates a signature.                                                     |
| Private key                 | Begin/end PEM labels containing `PRIVATE KEY` with at least one intervening non-whitespace character; include RSA/EC/OPENSSH/ENCRYPTED labels and escaped newline forms. Malformed material is a candidate with uncertain validity; public keys/certificates are negatives.                                                                                        |
| OAuth client secret         | Literal assigned to normalized `client secret` or `oauth client secret`, length ≥8; `client id` alone is a negative.                                                                                                                                                                                                                                               |
| Cloud credentials           | Sensitive variables `aws secret access key`, `azure client secret`, or `private key` in a service-account-shaped JSON object; pair IDs with secret fields within the same object or 10 adjacent lines. An access/account/client ID alone is not a secret.                                                                                                          |

Only fixed-length literal concatenations in the same file may be assembled, with total 64 KiB and at most 8 fragments. No eval, imports or data-flow execution. An environment lookup with unknown value is never replaced with the operator's environment. Frontend signals are explicit `use client`, known public-env prefixes, or relative path segments `frontend`/`client`; path-only exposure is inferred with at most medium confidence. Same-file binding use in a client initializer, authorization header, signing call or config assignment strengthens the use-context record. Alias resolution is limited to same-file direct assignments; uncertainty is recorded rather than guessed.

Classification features stored as redacted facts: relative file path; frontend/backend/config exposure; literal vs env reference; variable name; ±2 lines of already-redacted surrounding code; recognized family; apparent privilege; usage in client initialization, auth header or signing; placeholder markers and example location; evidence of bundling from known frontend conventions. For Next.js, `NEXT_PUBLIC_` values can be inlined into the browser bundle. [Next.js environment variables](https://nextjs.org/docs/app/guides/environment-variables). A directory named `server` alone does not establish secrecy; a file named `.example` alone does not establish a placeholder.

Classification outcomes: `likely_secret`, `public_identifier`, `placeholder`, `uncertain`. Confirm static exposure only when there is a non-placeholder literal, a strong family or secret-use signal, and an exposure fact such as committed config or client inclusion. Provider validity remains `not_tested`. A JWT role claim is decoded but never trusted as an authenticated privilege assertion. Backend environment lookups with no literal are not exposure findings. Backend hardcoded credentials still are.

### Placeholder and public-value handling

Exact obvious placeholders (`YOUR_API_KEY`, `CHANGEME`, `${VARIABLE}`, `<SYNTHETIC_SERVICE_ROLE_KEY>`, `TEST_ONLY_NOT_A_KEY`) or demonstrably nonfunctional examples are low-risk suppressed records when there is a candidate worth explaining. Do not suppress an arbitrary high-entropy value simply because it lives in an example file. Public OAuth client IDs and documented Supabase anon/publishable keys are negative cases unless a separate secret signal exists. A public client key plus weak RLS is handled by the RLS category, not by relabeling the client key as privileged.

User suppressions require rationale, scope (exact occurrence/rule, not directory wildcard), and an audit event. Reappearance with a changed fingerprint requires new review. The UI always keeps the redaction, even after a placeholder/public classification.

### Redaction pipeline and persistence

1. Accept bounded source bytes into transient process memory. Request-body logging, tracing payload capture, crash dumps and upload-to-disk spooling are disabled. Do not show uploaded contents in the browser preview; filenames/counts only.
2. Detect candidate spans before snippets are extracted. Decode at most two bounded layers of base64, hex, URL encoding, JSON escapes or escaped newlines; map derived spans back to the full original literal. Decode only candidate literals, not whole arbitrary files. Limit each decoded value to 64 KiB and total decoded data to 1 MiB per file.
3. Union overlapping spans and redact the entire secret-bearing literal/URI/key block. Do not preserve prefixes, suffixes, token lengths or decoded JWT content in prompts. Store family and whitelisted role classification only; redact surrounding strings too.
4. Create a keyed HMAC fingerprint in memory for within-project deduplication. Store only the digest and a project-local key in the private metadata store; neither goes to AI/UI/export. Never use a bare secret hash as a public identifier. Remove them with project deletion.
5. Generate candidate facts and minimal snippets from the redacted copy. Schema names, comments, paths, filenames, SQL errors, model text and exports pass the same secret detector and a stricter sink redactor. Omit a field entirely if safe representation is uncertain.
6. Drop raw buffers immediately after analysis. Persist only redacted findings and derived facts, never original source uploads. Managed runtimes cannot guarantee physical memory zeroization; avoid retaining references and disable dumps/swap where operator policy requires. This limitation must not become a false “memory wiped” claim.

For SQL uploads: run this pipeline first; if redaction would change executable schema content, reject that file and ask for a secret-free schema-only input. Do not execute a redacted approximation. Comments may be discarded by the AST admission renderer. Only admitted, credential-free schema is retained to reproduce retests.

Secrets in unsupported binary archives or unbounded encodings are not scanned: reject archives/binaries and report unsupported encoding when detected. Unknown encoding means incomplete coverage, not “no secrets.” Never send whole source files to Gemma as a workaround. Input text can still contain unrecognized secrets; use data minimization (metadata and normalized facts) as the principal model boundary rather than promising perfect regex redaction.

| Public identifier or proven placeholder                                                        | Info/suppressed; never a confirmed secret vulnerability                                   |

AI may suggest severity or interpretation but cannot validate a key, suppress the occurrence or mutate static evidence. Recommended actions: remove the literal, use server-only configuration, review issuer rotation/revocation and check relevant history. The tool applies no credential changes. A complete replacement-source rescan may show `fixed` with copy “Exposure removed from submitted files; rotation and previously published artifacts were not verified.” Omitting the affected file or uploading a partial tree cannot satisfy removal without an explicit complete manifest and deletion record (this document).

### Fixture honesty

Persist only conspicuous sentinels. Do not publish plausible private keys, provider tokens or JWTs, even randomly generated ones. Use two test layers: (a) grammar/unit tests on fragments, invalid-length/invalid-alphabet samples and transient generated buffers; (b) contextual tests with detector-candidate injection using explicit `synthetic=true` metadata. The demo frontend service-role case uses layer (b), visibly labeled synthetic; normal upload scanning cannot enable that adapter. It proves contextual classification/redaction/display, not recognition of a usable provider key. Precision/recall for these layers are reported separately, with injection cases excluded from end-to-end detection claims.

Suggested remediation aligns with the [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html); this tool measures artifact exposure and does not claim to implement the issuer's secret lifecycle.

## Verification engine

Repository-v2 admission allows bounded literal/UUID/time defaults. The seeder supplies explicit synthetic values for every column, including defaults; it never lets random/time defaults determine scenario identity. INSERT observers compare parameterized expected values in PostgreSQL (including JSON/date/numeric representations). Constraints are still enforced; failed shape/own-row controls remain inconclusive. Identity/generated columns, enums, unsupported FK dependencies and complex constraint solutions remain outside coverage. The seven test IDs, expectation authority and approval/retest gates are unchanged.

Requirements: FR-4, FR-9–FR-13, FR-16, NFR-1–NFR-5. This is the authoritative test registry and observation contract. No model-authored SQL, request URL, role, body or command reaches this engine.

### Eligibility and immutable scenarios

Build the matrix from the current catalogue, seed plan and all established expectation tuples. Evaluate all compatible tables, including those without static findings. Unknown tuples are recorded as skipped (`EXPECTATION_UNKNOWN`), never probed. Team rules are recorded as not testable (`TEAM_SEMANTICS_UNSUPPORTED`). Gemma recommendations only order eligible cases. The run begins after the user selects “Run verification”; this authorizes the entire displayed matrix, not individual AI-chosen probes.

`scenario_key` is SHA-256 of canonical JSON containing registry/test version, resource, operation, actor, target alias, seed digest, claims digest, expectation ID/revision, key bindings and mutation values. Exclude run ID, timestamps and schema/patch digest so baseline/retest keys compare equal. The run manifest separately records baseline and patched schema digests, engine/image versions and patch. A changed seed/expectation/claim/test implementation requires a new baseline, not a fix-verified retest.

Each entry has a versioned application query template, required grants, required controls and observer assertions.

### Low-privilege role and claims simulation

Trusted bootstrap creates `anon` and `authenticated` as NOLOGIN, NOSUPERUSER, NOBYPASSRLS, NOCREATEDB, NOCREATEROLE roles. `verifier_login` is LOGIN, NOINHERIT, NOSUPERUSER, NOBYPASSRLS and is granted SET membership only in those two roles; it owns no admitted object and cannot SET ROLE to schema loader or bootstrap. Schema loader owns application tables; a separate local setup connection may use bootstrap privileges only for creation/seeding/observation/cleanup. No setup observations are labeled as low-privilege attack results.

Each probe checks `session_user=verifier_login`, `current_user` after role switch, role flags, non-ownership and `row_security=on`. Fail before operation if any invariant is false. Never grant missing actor privileges to make a test executable; preserve uploaded semantics. Do not set `row_security=off` or force RLS on/off for tests.

Each probe uses transaction-local role, synthetic request claims, `statement_timeout=5s`, `lock_timeout=1s` and `row_security=on`. Roles come from application enums; claim values are parameters.

A claims: `{"sub":"00000000-0000-4000-8000-000000000001","role":"authenticated","aud":"authenticated"}`. B ends in `0002`. Anon claims: `{"role":"anon"}` with no sub; `auth.uid()` must be null. No service role claim. The trusted SQL STABLE SECURITY INVOKER helpers first normalize claims using `COALESCE(NULLIF(current_setting('request.jwt.claims',true),''),'{}')::jsonb`; `auth.uid()` returns `NULLIF(claims->>'sub','')::uuid`, `auth.role()` returns `claims->>'role'`, and `auth.jwt()` returns claims. Here claims denotes the normalized expression, not an uploaded identifier. Qualify built-ins/use fixed search_path and grant only necessary schema USAGE/function EXECUTE. An empty/missing GUC produces null for uid, not a JSON parse exception. Bootstrap `auth.users` has only synthetic ID records and is not an attack target.

These settings imitate a portion of [PostgREST's transaction context](https://docs.postgrest.org/en/stable/references/transactions.html). They do not validate JWT signatures, refresh sessions, execute auth hooks or imitate production claim issuance. Policies using unsupported custom claims require a reviewed synthetic claims fixture; otherwise `CLAIMS_UNMODELED`. Claim fixtures are data, never arbitrary JWT signing keys. Changing them creates a new baseline.

Use a fresh dedicated `pg` client for each case and close it after completion; rollback in finally, never return a possibly contaminated session to a shared pool. Mutation cases deliberately commit only within the disposable replica for observer verification (below); the final reset/destroy still runs. Record connection failure without attempting further SQL in an aborted transaction.

### Seeder and per-case isolation

Implemented seeding uses single-column primary keys, auth.users ownership FKs and fixed UUID, text/varchar/char, smallint/integer/bigint/numeric, boolean, date/timestamp/timestamptz and JSON/JSONB values; unsupported nullable values may be null. Bytea/enum adapters, arrays, ranges, spatial/composite types and custom domains are outside achieved coverage. Supply explicit values even for admitted UUID/time defaults; never let randomness/time define scenario identity. Validate target existence, owner, exact keys and each operation's shape using the separate setup identity. Enforce all constraints; never disable or loosen them. INSERT observers compare typed values in PostgreSQL, including JSON/date/numeric representations.

Deterministic seeding uses fixed reciprocal A/B UUIDs, seed version 1 and table/column ordinal. D-18 bounds the design to 500 rows and 20 candidate assignments per row; the current seeder supplies fixed assignments rather than solving arbitrary constraints. Inventory constraints before creating values. Broader design targets include alternate unique/composite locators, FK dependency graphs/support rows, nullable/deferrable cycles, enums, identity/sequence/default adapters and bounded CHECK solutions. They are not implemented coverage. No locator → NO_ROW_LOCATOR; unsupported type/default/check/FK → the corresponding reason from `finding-model-and-lifecycle.md`. No mutable non-owner column prevents neutral UPDATE, not unrelated operations. Missing/unmodeled claims and team semantics stop dependent probes. Never use arbitrary AI/SMT SQL or real rows.

Before **each** matrix case, the setup connection restores the same complete seed plan (truncate only admitted synthetic tables in dependency-safe fashion; reset owned sequences; reseed). All other replica clients are quiescent. SELECT probes roll back. Mutations use one low-privilege transaction, commit on success, then a separate setup observer checks exact post-state: changed neutral value, disappeared target, inserted owner, or owner transfer. A failed statement is rolled back and must leave data unchanged. Restore seeds before the next case, even after failure. This avoids relying on a privileged second connection seeing another transaction's uncommitted writes. It costs extra seeding but is predictable at hackathon scale.

Use mutation command row count and the setup observer together; avoid `RETURNING` solely for evidence because it introduces additional SELECT-policy effects. WHERE uses the exact key and required SELECT privilege/control is recorded. Reject user triggers and rewrite rules in the default admission profile so they cannot swallow changes or forge observer assumptions. Never report ALLOW if row count and actual mutation disagree (`OBSERVER_MISMATCH`). Cross-user deletion fixtures must not have dependent rows that make DELETE fail; otherwise that case is `FK_DELETE_BLOCKED` and is not called RLS denial.

### Expected versus observed classification

| Result                                                                                   | Preconditions                                                                                                                | Observation / consequence                                                                   |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Exact foreign target returned                                                            | Identity, target owner/existence and positive controls validated                                                             | allow; expected deny → mismatch and confirmation                                            |
| Exact mutation succeeded                                                                 | One affected row, observer confirms intended change, controls valid                                                          | allow; compare against frozen expectation                                                   |
| Zero matching rows / zero affected rows                                                  | Target exists, exact predicate/bindings valid, required privileges present, controls pass, no unsupported semantics/triggers | deny / `rls_filter`; statement may be filtered by SELECT as well as command-specific policy |
| SQLSTATE 42501 specifically identifying row-security check rejection                     | Required table/column/sequence/schema privileges validated; constraint-valid insert/update shape; controls pass              | deny / `rls_check`                                                                          |
| SQLSTATE 42501 identifying missing required privilege                                    | Catalogue confirms exact missing privilege and no missing expected-allow control                                             | deny / `grant`; report tested access blocked by grant, not by RLS                           |
| 42501 with ambiguous origin                                                              | Cannot distinguish policy/check/grant/function permission                                                                    | error / `AMBIGUOUS_PERMISSION_ERROR`; inconclusive                                          |
| 23502/23503/23505/23514 (NOT NULL/FK/unique/check), cast errors, missing object/function | Any                                                                                                                          | error / `CONSTRAINT_OR_SETUP_ERROR`; never deny                                             |
| Timeout, deadlock, network failure, unexpected row count/side effects                    | Any                                                                                                                          | error with reason; inconclusive                                                             |
| Own-row expected-allow test denied/errored                                               | Related negative case otherwise appears denied or allowed                                                                    | Related case inconclusive / `POSITIVE_CONTROL_FAILED`; repair setup before confirmation     |

Error details are examined only transiently with `lc_messages=C`; persist SQLSTATE plus a fixed reason enum and sanitized object reference. Do not classify every 42501 as RLS. Baseline `deny_all` intentionally has no own-row ALLOW requirement; prove query/data validity with setup controls, record `control_result_ids=[]` for absent positive controls, and explicitly report grant-based denial when applicable. An anonymous deny-all probe does not fail merely because anon cannot access any rows. `all_rows` expected-allow denial is an availability/expectation mismatch, not an unauthorized-access vulnerability and cannot confirm one.

Result fields and finding aggregation are defined in `finding-model-and-lifecycle.md`. `not_testable` is not stored as `observed=deny`; it is `not_run` or `error`, inconclusive with a reason. Run coverage: planned = all generated cases including skips; executed = cases that actually issue a probe (including errored probes); skipped = cases with no probe; planned = executed + skipped; errored ⊆ executed; not_testable spans skipped/errored and is not added again to totals.

### Not-testable reasons and lifecycle

Canonical reason codes are the TestReasonCode enum in `finding-model-and-lifecycle.md`: `NO_ROW_LOCATOR`, `OWNER_BINDING_MISSING`, `TYPE_UNSUPPORTED`, `DEFAULT_UNSUPPORTED`, `CHECK_UNSATISFIED`, `FK_CYCLE_UNSUPPORTED`, `FK_TARGET_UNSUPPORTED`, `FK_DELETE_BLOCKED`, `NO_MUTABLE_COLUMN`, `CLAIMS_UNMODELED`, `TEAM_SEMANTICS_UNSUPPORTED`, `UNSUPPORTED_SCHEMA_SEMANTICS`, `POSITIVE_CONTROL_FAILED`, `CONSTRAINT_OR_SETUP_ERROR`, `AMBIGUOUS_PERMISSION_ERROR`, `OBSERVER_MISMATCH`, `IDENTITY_ASSERTION_FAILED`; infrastructure reasons `REPLICA_UNAVAILABLE`, `STATEMENT_TIMEOUT`, `CONNECTION_LOST`, `JOB_DEADLINE`, `CANCELLED`; and `EXPECTATION_UNKNOWN`, `UNEXPECTED_DB_ERROR`. Infrastructure reasons block conclusions and permit a fresh retry; unknown database errors require investigation before retry. EXPECTATION_UNKNOWN retains needs_expectation, not not_testable. No mutable non-owner column blocks neutral UPDATE scenarios but need not block SELECT/INSERT/DELETE.

Replica lifecycle: allocate opaque ID and random local credentials → start approved image with quotas → bootstrap trusted roles/helpers → apply admitted schema atomically as restricted owner → introspect → seed → run matrix → collect redacted evidence → destroy container/data/network. Retest repeats from original admitted schema, applies the approved patch, then uses the identical seed plan and matrix. TTL is 10 minutes maximum for abandoned containers, reconciled on startup and every minute. Keep only redacted evidence and admitted schema under the 24-hour retention policy.

Bind a dynamically allocated PostgreSQL port only to `127.0.0.1` on a dedicated internal container network. Preflight must prove no replica egress and reachable host-side loopback on the target Docker runtime; fail closed if the runtime cannot enforce this. No host/project mounts or privileged containers; bounded tmpfs for data and required writable runtime paths. The worker's Docker command arguments are fixed except validated opaque IDs/ports/limits; no shell interpolation of user content.

Fidelity gaps always shown: synthetic rows; simplified auth.users and local auth helpers; untested JWT authentication/custom claims/auth hooks; no storage policy, edge function or application-route execution; excluded extensions/functions; omitted production grants not supplied in schema; differences in server version/collation. Optional Supabase mode adds local JWT/PostgREST fidelity but retains these scope limitations and has a separate run mode/dataset segment.

## Remediation and retest

Requirements: FR-15, FR-16, FR-22, FR-23. The application renders a typed intent as a concrete patch; a human approves that exact patch for a disposable replica.

Only `owner_select_v1` is currently implemented; the other typed template IDs below remain design targets and return `PATCH_UNSUPPORTED`.

### Constrained patch format

The brief asks for Gemma remediation as a migration while forbidding arbitrary AI SQL. D-07: Gemma selects a typed remediation intent; the application renders and validates the migration. The user still reviews a SQL migration attributed as “Gemma suggestion, application-rendered patch.” Free-form model SQL is never accepted, including after approval. Unsupported fixes remain manual guidance with no apply button.

```typescript
type MigrationPatch = {
  schema_version: '1.0';
  id: Id;
  finding_id: Id;
  project_id: Id;
  input_revision: number;
  baseline_run_id: Id;
  baseline_schema_digest: Digest;
  expectation_revision_ids: Id[];
  template_id:
    | 'owner_select_v1'
    | 'owner_insert_v1'
    | 'owner_update_v1'
    | 'owner_delete_v1'
    | 'enable_rls_v1';
  resource: Resource;
  policy_name: string | null;
  owner_column: string | null;
  migration_sql: string;
  patch_digest: Digest;
  preconditions: string[];
  rationale: string;
  risks: string[];

  status: 'proposed' | 'approved' | 'applied' | 'failed' | 'superseded';
```

Digest covers exact UTF-8 SQL bytes plus canonical resource/baseline/expectation/template metadata. Approval payload must match these exact values. Post-render parsing permits only the statements emitted by the selected template, on that exact table/policy. All identifiers are catalogue-resolved and correctly quoted, never directly spliced from model text. A changed patch, model regeneration, schema, owner mapping or expectation revokes approval. SQL preview is read-only; editing intent regenerates/revalidates/reapproves. No arbitrary SQL editor in v1.

| Template          | Preconditions                                                                                                                                                    | Exact change                                                                   |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `owner_select_v1` | Declared or visibly inferred owner-only SELECT, UUID owner mapping, one applicable authenticated permissive SELECT policy, no ALL policy/cross-command ambiguity | ALTER POLICY selected policy USING (`auth.uid() = owner_column`)               |
| `owner_insert_v1` | Same constraints for INSERT                                                                                                                                      | ALTER POLICY selected policy WITH CHECK (`auth.uid() = owner_column`)          |
| `owner_update_v1` | Same constraints for UPDATE; SELECT owner access already valid                                                                                                   | ALTER POLICY selected policy USING and WITH CHECK owner predicate              |
| `owner_delete_v1` | Same constraints for DELETE                                                                                                                                      | ALTER POLICY selected policy USING owner predicate                             |
| `enable_rls_v1`   | RLS currently disabled, expected access established, admitted existing policies reviewed for all operations                                                      | ALTER TABLE selected table ENABLE ROW LEVEL SECURITY; preserve policies/grants |

Restrictive policies may remain only if renderer validates that replacing the single permissive policy preserves them and retest covers their expected behavior. Multiple applicable permissive policies, complex shared-team rules, mutable owner semantics, custom helpers or policies serving additional roles → unsupported automatic remediation. Do not merely add a narrow permissive policy alongside a broad one: OR composition can leave the bypass intact. Role scope on the existing policy must be exactly authenticated; `PUBLIC` or combined anon/authenticated policies require a separate reviewed design and are unsupported by these owner templates.

The SQL is a downloadable user migration; runtime applies its single validated inner statement in a managed transaction to avoid nested transaction behavior. Preview/export and runtime share the same canonical statement AST and digest. The migration is not idempotently replayed without baseline precondition checks.

### Approval, application and regression gates

1. Require a current confirmed RLS baseline, valid target mapping and established expectation; show before evidence, proposed SQL, rationale, affected policy, known limitations and regression list.
2. User action “Approve and apply to replica” records the local operator, exact digests and expectation revisions. This does not deploy anything or authorize a production connection.
3. Create a fresh replica from the original admitted schema. Verify its normalized catalogue digest matches baseline before applying. If grants/version/environment drifted, stop with `BASELINE_DRIFT` and require a new baseline.
4. Apply the validated patch as the restricted table owner under timeout in a transaction. Roll back on any error, record sanitized reason and set `fix_not_verified`. Never continue on a partially applied schema.
5. Introspect again and assert the catalogue diff contains only the approved changes. Reuse original seed plan, registry, claims and scenario keys. Missing or changed keys fail identical-scenario comparison.
6. Run the complete original table matrix, plus existing established-operation matrices of FK-dependent tables when the patch affects them. Always run the triggering case, reciprocal case, all own-row cases, any previously allowed public accesses, and owner-transfer/foreign-owner-insert regressions if applicable. Additional tests are labeled additional; original evidence is not replaced.
7. `fixed` requires every previously confirmed unauthorized case in scope now conclusively denied, every expected-allow regression passing, no new unexpected allows, no required skipped/errored cases, valid role/setup controls, and identical original scenario keys. Passing the flagship alone cannot hide failed UPDATE/INSERT sanity checks. Unchanged inconclusive baseline cases prevent the label “complete matrix fixed”; use `fix_not_verified` until the required scope is testable.
8. Store new Run and RetestResult, preserve the baseline, destroy replica. If still allowed or own access is broken, show `fix_not_verified` with the exact failure. New valid attack confirmation can be linked, but the attempted-fix verdict remains failed.

If user changes intent to public after the baseline, the old “mismatch” is historical and cannot be used to claim a fix. If an inferred expectation remains inferred, fix wording remains conditional: “Fix verified against the inferred owner-only expectation in the replica.”

### Credential remediation and rescan

Credentials do not receive SQL patches or replica tests. Explain removal, server-side configuration and issuer rotation steps without a provider action. A rescan uses a complete replacement input manifest, explicit deleted paths, same source scope and analyzer version; scan all submitted files for the occurrence/fingerprint and new appearances, not only the original line. A partial upload or unsupported file prevents verified removal. Do not persist the original secret to compare; use the local keyed fingerprint and contextual identity. `fixed` means the submitted artifact exposure was removed. Rotation, revocation, Git history and previously shipped client bundles remain unverified and are explicitly listed.

### Export

RLS export contains: `migration.sql` with the approved rendered change and baseline preconditions in comments; `report.json` using versioned finding/run/result contracts; human-readable `report.md` with expected-vs-observed rows, expectation source/revision, before/after hashes, test versions, synthetic identities, regression/coverage counts and fidelity gaps. Credential export omits migration and includes static evidence/removal scope plus unverified rotation reminder.

No uploaded source, database password, discovered secret, raw model response, Docker inspect output or production credential goes into an export. Downloads require explicit user action and an outbound redaction pass. The UI says “Review and apply this migration in your own project workflow”; the application has no deployment action.
